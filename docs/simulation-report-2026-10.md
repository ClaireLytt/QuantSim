- **昼夜权重**：0-6 点低谷(0.1~0.2)，9-11/19-22 高峰(0.9~1.0)，用户发起间隔 ∝ 1/权重。

  settle/daily_start 6、register 2、undo 2；**异常操作**：double_settle 3、slow_trade 3、double_daily 2、

- **房间生成**：每 30min 批量建 3~10 个房间（各 2~8 人，TTL 30min）→ 制造"集中到期"突发（X1 触发条件）。
- 500 用户独立行为流 + 房间生成器 + 内存剪枝进程，事件优先队列按时间推进。

## 四、关键发现

1. **✅ FTA"当前不成环"被实测证实**：94 万次操作、含 2% undo + 6% settle 高频交错，**死锁 = 0**。
   验证了 docs/fault-tree-analysis 的 TB1 分析——锁序反转当前靠"同 session 串行 + account 按 session 隔离"
   确实拆除了环。
2. **✅ 本轮修复在长时负载下稳定**：零 5xx、daily 双开/注册/重复结算全部正确转 400、零价守卫全接住、
   房间强结零失败零状态不一致——13 bug 修复在 72h 压力下无回归。
3. **⚠ X1 雪崩在"常规行为模型"下未触发**（池峰值仅 7/20）：这是**诚实且重要**的结论——X1（房间强结读
   路径雪崩）是**最坏情况**，需要比本模型更极端的"房间高度集中到期 + 同一时刻大量并发 view + 成员恰在
   慢交易持锁"才会把连接占用推到饱和。本仿真的房间到期是分散的、slow_trade 与 room_view 的时间重合率
   低，所以池峰值远未触顶。**结论**：常规流量下 pool=20 足够安全；X1 仍是需用**对抗性故障注入**
   （FI-1/FI-7，手动制造极端聚簇）才能复现的高危**尾部**风险，而非常规风险。

## 五、瓶颈点与优化建议

- **锁等待集中在 session/account 行锁**（6.3 万次）：单对局高频操作(trade/settle/undo)串行化——这是
  **正确的串行**（同对局本就该串行），非瓶颈；但印证了"结算在读路径触发"会把这些锁拖进房间读热路径
  （技术债 D1.1）。
- **连接池 20 对常规负载充裕**（峰值 7），但**X1 尾部风险仍在**：建议保留 pool=20，并按 FI-7（临时调小池
  跑 FI-1）主动找饱和拐点，而非等线上触发。
- **根治方向**：仿真再次指向同一结论——**把房间强结移出读路径 / 异步化**（技术债 P0 D1.1），从根本上
  消除 X1 的尾部风险，而不是靠调大连接池被动兜底。
