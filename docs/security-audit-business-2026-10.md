# QuantSim 业务逻辑安全审计（渗透推演）· 2026-10

> 范围：排行榜积分、房间结算、每日挑战/每日一猜奖励、藏品/声望、积分商店。
> 方法：区分**服务端权威状态**（可被公开榜/经济利用）与**客户端本地状态**（只骗自己），
> 对前者逐条推演时序/状态绕过/并发攻击链。**本审计发现 2 个真实经济漏洞**（SEC-1/SEC-2），
> 并确认多处防护做得正确。

---

## 一、攻击面与资产分层

| 资产 | 权威方 | 公开影响 | 攻击价值 |
|---|---|---|---|
| 积分余额 / 积分榜 | **服务端** `user_points` + PointsService | 有（公开积分榜 + 兑换"奖品"） | **高** |
| 对局收益榜 / 夏普榜 | **服务端** game_sessions | 有（公开榜） | 中 |
| 每日挑战榜 / 奖励 | **服务端** uk_user_daily | 有 | 中 |
| 藏品收集 / 声望 / 段位 / 每日一猜 | **客户端** localStorage (qs_progress/qs_reborn) | **无公开榜** | 低（只骗自己） |
| 道具 (peek/undo/fast) | 服务端 user_points 字段 | 影响对局 | 中 |

**关键判断**：藏品/声望/每日一猜是纯客户端，伪造只影响自己、不进任何公开榜——**非安全重点**。
真正的攻击面是**服务端积分经济**与**公开收益榜**。

---

## 二、漏洞清单与攻击链

### 🔴 SEC-1（高）无限结算刷积分 —— 积分底分无每日上限

- **证据**：`PointsService.awardSettle`：`earned = 50`（**无条件底分**）+ beatAi(+30) + beatHold(+20) +
  winStreak(+10×streak) + TASK_SETTLE(+30/日) + TASK_DAILY(+40/日)。**只有后两项日封顶，+50 底分每次结算都发。**
- **放大器 ①（winStreak 无封顶）**：`setWinStreak(beatAi ? streak+1 : 0)`，`earned += 10 * streak`，**streak 无上限**。
  对 EASY AI 易胜 → streak 线性增长 → 第 N 局仅 streak 奖励就 +10N（第 100 局 +1000/局）。
- **放大器 ②（登录用户 start 不限流）**：`GameController.start` 仅对**游客**按 IP 限流，**登录用户无限开局**。
- **放大器 ③（结算无需交易）**：`settle` 只要对局 `IN_PROGRESS`；`start → settle` 立即可成，无需任何 tick/trade。
- **攻击链**：
  ```
  登录 → loop { POST /api/game/start  →  POST /api/game/{id}/settle }   (每轮 ~2 请求, +50 起)
       → 配合 beatAi 版本 (对 EASY 下几手必胜) → winStreak 无限涨 → 每局 +50+30+10·streak
       → 脚本化数千轮/小时 → 碾压积分榜 + 兑换全部"奖品"
  ```
- **攻击前提**：一个注册账号（非游客）。无需任何客户端篡改，纯合法 API 调用。
- **危害**：积分榜完全失真；积分经济（商店/盲盒）崩溃。虽奖品是模拟（有免责声明），但**公开榜公信力**与
  活动公平性被摧毁。
- **现有防护评估**：**不足**。awardReborn/academy 用 taskFlag 日封顶（注释自述"无套利空间"），但
  awardSettle 的 +50 底分**恰恰没有**这个封顶——设计假设"结算是真实对局所以自限速"，而**结算无需交易**
  使该假设不成立。

### 🔴 SEC-2（高）盲盒正期望 —— 积分 money pump

- **证据**：`redeem("blindbox")` 成本 **500**，收益 `100 + rand[0,900]` = 均匀分布 **[100,1000]，期望 550**。
- **期望净收益 = 550 − 500 = +50 / 次**（正 EV）。
- **攻击链**：
  ```
  有 500 分 → loop { POST /api/me/points/redeem {blindbox} }
           → 每次期望 +50, 大数定律下必然净赚 → 无限刷分
  ```
- **攻击前提**：500 起始积分（签到几天即得，或配合 SEC-1）。
- **危害**：独立于 SEC-1 的第二条无限刷分路径；且这是**经济设计缺陷**，并发行锁再严也拦不住（是 +EV 不是竞态）。
- **现有防护评估**：**不足**。并发安全（行锁）到位，但**定价错误**：盲盒成本必须 ≥ 期望收益（≥550）才非 +EV。

### 🟡 SEC-3（中）收益榜无按用户去重 —— 灌水占位

- **证据**：`GameSessionRepository.findLeaderboard` 按 `final_return_rate DESC` 取 TOP N，**无 `GROUP BY user`**。
- **攻击链**：登录 → 无限开局（SEC-1 放大器②）→ 保留运气好的高收益局 → 一个用户**多条**记录占据 TOP N 多个名次。
- **攻击前提**：注册账号 + 多次开局（手动交易已限收盘价成交，无上帝视角套利，但随机开局总有高收益窗口）。
- **危害**：收益榜被单用户灌水；挤占真实玩家（叠加本轮已修的"测试账号挤位"同类问题）。
- **现有防护评估**：部分——手动交易套利已堵（收盘价成交），但**榜单去重缺失**使"多次尝试取最优"可行。

### 🟢 SEC-4（低）客户端成就 claim 无法服务端复核

- **证据**：`/api/me/points/academy-claim`、`/reborn-claim`——客户端声称"我通关了名场面/达成天命"，服务端无法复核
  （关卡在前端跑）。
- **防护**：`claimTask` 用 taskFlag **日封顶 +40/kind**（注释明示"无刷分空间"）。
- **评估**：**可接受的设计取舍**——任何人都能每日白嫖 +40（不做成就也能领），但**全员平等、有封顶**，非差异化套利。
  模拟游戏语境下成本可控。建议知悉即可。

## 三、确认做对的防护（正面结论，勿误改）

- ✅ **积分并发全行锁串行化**：`getOrCreate` 走 `findWithLockByUserId`（悲观锁），signin/spin/redeem/awardSettle
  对同一用户串行——**无双重签到、无超额兑换、无负余额、无道具并发翻倍**。并发竞态在积分侧**已堵死**。
- ✅ **服务端日界用 `GAME_ZONE`（上海）**：签到/转盘/taskFlags/每日挑战 uk 全按**服务端日期**，客户端改钟
  **无法跨零点重复领奖**（每日一猜的客户端时钟只影响本地无奖励防刷）。
- ✅ **冒名已收口**：`UserService.resolve` 已登录以会话为准、游客撞注册名被拒——无法顶他人身份入榜。
- ✅ **兑换余额检查原子**：行锁内"查余额→扣减"原子，无 TOCTOU 超扣。
- ✅ **幸运转盘服务端随机**：奖品由服务端定（防前端自选）。
- ✅ **每日挑战唯一键**：`uk_user_daily` 保证每人每天一局一奖，无重复领 +40。

## 四、加固方案

### 针对 SEC-1（无限结算刷分）
1. **结算底分日封顶**（首选，最小改）：把 +50 底分也纳入 `claimTask` 日封顶体系，或设每日结算发分上限
   （如每日前 N 局发分，超出只记成绩不发分）。
2. **winStreak 封顶**：`winStreak` 设上限（如 ≤10），`earned += 10 * min(streak, CAP)`——拆放大器①。
3. **登录用户开局限流/限量**：对登录用户也加每日开局数上限或限频，拆放大器②。
4. **结算有效性门槛**：发分要求对局有实质参与（至少 1 笔交易 / 推进到结算日），拆放大器③——
   "空开空结不发分"。

### 针对 SEC-2（盲盒 +EV）
- **定价修正**：盲盒成本 ≥ 期望收益（成本 ≥ 550，或收益区间下调使期望 < 成本）。使其成为**负 EV 的娱乐消费**
  而非套利。或设每日盲盒次数上限。

### 针对 SEC-3（榜单灌水）
- **按用户去重**：榜单查询 `GROUP BY user_id` 取每人最佳一条（或 `DISTINCT` + 窗口函数取 per-user top1），
  一个用户在榜上只占一个名次。

### 校验点 / 幂等 / 防重放（通用设计原则）
- **幂等**：一次性奖励用**唯一键/状态位**兜底（每日挑战 uk、taskFlag 已是范例）；结算发分应绑定
  `session_id` 唯一（每个对局只发一次分，已隐含；但"开无限对局"绕过了"每对局一次"的限制——所以要在
  **对局数/有效性**层面限，而非只在"每对局一次"层面）。
- **防重放**：状态变更接口保持 POST + 服务端幂等键；"领奖"类绝不信任客户端断言的成就（SEC-4 已用 taskFlag）。
- **经济校验点**：任何"消耗 X 得 Y"的兑换，上线前核**期望收益 ≤ 成本**（SEC-2 的教训）；任何"动作得分"
  核**单位时间最大可得分**是否被动作成本自然限制（SEC-1 的教训——结算成本太低）。
- **发分服务端化**：所有发分路径已在服务端（好）；继续坚持——前端只触发、不自算分。

## 五、风险矩阵与处置优先级

| 漏洞 | 利用门槛 | 自动化难度 | 危害 | 优先级 |
|---|---|---|---|---|
| SEC-1 无限结算刷分 | 低（1 注册号） | 易（2 请求/轮，脚本化） | 高（榜单+经济失真） | **P0** |
| SEC-2 盲盒 +EV | 低（500 分起步） | 易（1 请求/轮） | 高（无限刷分） | **P0** |
| SEC-3 收益榜灌水 | 低 | 中（需多局挑好的） | 中（榜单公平） | **P1** |
| SEC-4 客户端成就 claim | 低 | 易但有封顶 | 低（全员平等） | P2（知悉） |

---

**审计结论**：QuantSim 的**并发/时序/冒名/跨零点**类防护做得扎实（行锁串行化 + 服务端日界 + resolve
收口），本轮 13 bug 也堵住了手动交易套利与测试账号挤位。但渗透推演暴露了**两个此前未覆盖的经济设计
漏洞**——SEC-1（结算发分无成本约束）与 SEC-2（盲盒正 EV），二者都可被单个合法账号脚本化无限刷分，
**是当前最该堵的 P0**。加固核心原则：**"动作得分"必须被动作成本自然限制；"消耗得收益"必须负 EV**——
这两条经济不变量应纳入发分/兑换接口的上线校验清单。
