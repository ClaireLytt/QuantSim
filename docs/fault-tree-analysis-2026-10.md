# QuantSim 故障树分析（FTA）· 2026-10

> 针对两大顶层故障事件做穷尽式故障树推演，把本轮已修复的 13 bug 作为已知叶子节点，
> 并推演**多故障并发叠加**的复合场景、识别时序竞争与竞态窗口。
>
> **推演基线（已核实的架构事实）**：
> - 单实例 Spring Boot + MySQL InnoDB，**隔离级别默认 REPEATABLE READ**（未显式配置）。
> - 悲观锁 `SELECT ... FOR UPDATE`：session / account / position / user_points / room。
> - **正常锁序**：`session → account → position`（trade/tick/settle 一致）。
> - **⚠ 锁序反转点**：`undo` 走 `session → user_points → account`；`settle` 走 `session → account → user_points`——account 与 user_points 顺序相反。
> - 房间到期**强制结算在 `view()` 读路径同步触发**，持 `room` 行锁、对每个成员走 `settleIsolated`（REQUIRES_NEW 独立事务/独立连接）。
> - Hikari 池本轮已显式配 20（原默认 10）。
>
> 符号：`[OR]` 或门（任一子因即触发）、`[AND]` 与门（全部子因同时才触发）、`{已修}` 本轮修复的叶子、`{残留}` 未闭合风险、`{设计}` 有意行为。

## 一、故障树 1：顶层事件 **T1 = 对局结算失败 / 结算结果错误**

├─[OR]

## 三、单点故障 / 事务边界漏洞 / 竞态窗口 / 时序竞争

### SPOF 单点故障
- **SPOF-1 单实例 + 单 MySQL**：无水平扩展，应用或 DB 宕 = 全站不可用。限流/会话/榜单缓存都是进程内。
- **SPOF-2 房间读路径承载写**：`view()` 对到期房间**同步强结**并持 `room` 锁——房间读是热路径，一旦强结慢（成员多/锁等待），该房间**所有** view/join 阻塞。读写耦合在单点。

### TB 事务边界漏洞
- **TB1 锁序反转（最隐蔽）⚠**：
  - `undo`：`session → user_points → account`
  - `settle`：`session → account → user_points`
  - account 与 user_points 顺序**相反**。**当前不成环**，仅因两个偶然前提：
    (a) 同一 session 的 undo/settle 被 **session 行锁串行化**，不能同时越过；
    (b) account 按 session 隔离，不同 session 的 undo/settle 锁的是不同 account。
  - **这是"靠巧合拆除的雷"**：若未来 (a) 一个用户的两个 in-progress 对局并发 undo+settle，且 (b) 某特性让它们共享一个 user 级可写资源并以相反序加锁 → **真死锁**。属**潜在架构陷阱**，非当前活跃 bug。
- **TB2 REQUIRES_NEW 跨连接自阻塞**：`view()` 外层持 `room` 锁+连接 C1，`settleIsolated` 用连接 C2 锁 `session`。当前 C2 不碰 room、无成环；但**单请求占 2 连接**，且 C2 的 session 锁可能被并发 trade 持有而阻塞，此间 C1+room 锁被钉住。
- **TB3 check-then-act 非原子**：daily `start` 的 `findByUserIdAndChallengeDate(空)` → insert。**REPEATABLE READ 快照下 find 看不到并发已提交行**，故 find 兜不住并发 → 真正的护栏是 `uk_user_daily` 唯一键 + catch 转 400（已修）。注册同理（唯一键 + catch）。

### RW 竞态窗口
- **RW1 房间强结窗口**：`room` 锁持有时长 = 遍历+结算最多 8 成员，每员可能等待并发 trade 持有的 session 锁。窗口 = Σ(单员结算 + 可能的锁等待)。期间该房间 view/join 全阻塞。
- **RW2 每日一猜跨零点**（客户端）：开局落 `date=本地今天`，若本地时钟与服务端 `GAME_ZONE` 不一致，窗口 = 两时钟差。{设计, 纯本地防刷, 无服务端奖励, 危害有限}
- **RW3 限流清理窗口**：key 数 > 10000 触发 `removeIf` 与 `computeIfAbsent` 交错的纳秒级窗口，`putIfAbsent` 兜底后极端下仍可漏记 1 跳。{已兜底}
- **RW4 qs_progress 双写（前端）**：auth 云端恢复直接 `setItem` 原始串，绕过 academy 内存 `prog`；恢复后到下次刷新间，内存与存储不一致。{残留-低, 前端}

### TR 时序竞争（跨请求）
- **TR1**：并发同名注册 / 同人双开每日 → 唯一键串行化 → 1 成 N 败(400)。{已修}
- **TR2**：多房间同时到期 + 并发 view → 连接 2× + room 锁堆积（见 X1）。
- **TR3**：成员 m 正在 trade（持 session_m 锁）时，房间 view 的强结要锁 session_m → 强结阻塞 → room 锁延长持有。

## 四、高风险复合故障场景清单（多故障叠加 + 触发时序）

### X1 多房间集中到期 + 并发访问 + 成员在玩 【高概率·高破坏】
- **触发时序**：
  1. 活动结束等原因，T 时刻多个房间同时到期。
  2. 多用户几乎同时打开各自房间页 → 多个 `view()` 并发，每个持 `room_i` 锁 + 触发 8 成员强结。
  3. 部分成员此刻正在 trade（持 session 锁）→ 对应强结的 `settleIsolated` 阻塞。
  4. 每个 `view()` 占 2 连接且被钉住（外层等内层）。
- **现象**：连接池(20)快速耗尽 → 新请求 `Connection is not available`；被强结房间的 view/join 全部阻塞/超时。
- **危害**：**局部雪崩**——不仅房间功能，所有需要 DB 连接的接口（含榜单、对局）在池耗尽期间一起变慢/失败。
- **叠加的底层叶子**：SPOF-2 + TB2 + RW1 + TR2 + TR3。

### X2 跨午夜 + 并发房间结算 + 榜单查询同时发生 【中概率·中破坏】
- **触发时序**：
  1. 临近零点，赛季/每日边界切换。
  2. 同时有房间到期强结（写 game_sessions.status=SETTLED）+ 大量榜单查询（读 game_sessions ORDER BY return）。
  3. 强结的写锁与榜单读（RR 快照读, 通常不加锁）并发。
- **现象**：榜单读走 MVCC 快照一般不被写阻塞；但若榜单查询恰好在强结大批提交之间，**赛季归属以 `season` 字段为准**，跨零点新局记新赛季——不会串季（season 在开局固化）。榜单数据正确，但强结批量提交期间写放大。
- **危害**：以性能抖动为主，数据一致（season/challengeDate 开局固化）。
- **叠加叶子**：RW1 + 榜单读写并发。

### X3 弱网中断 + 部分成员结算失败 【中概率·低破坏】
- **触发时序**：
  1. 房间到期，`view()` 触发强结。
  2. 成员 m2 的标的行情此刻缺失（数据管道异常）→ `settleIsolated(m2)` 抛 `BusinessException`。
  3. 同时发起 view 的用户弱网，响应未回即刷新重试。
- **现象**：m2 独立事务回滚、不污染房间；房间仍迁 SETTLED；弱网重试因幂等再次 200。
- **危害**：低——本轮 #3 已兜底；m2 保持未结算（可后续人工/重试结算），失败进 warn 日志。
- **叠加叶子**：A1.1{已修} + A3.3 + C22。

### X4 并发注册 + 行情零值同时触发 【低概率·低破坏】
- **触发时序**：
  1. 批量脚本并发注册同名（唯一键冲突）。
  2. 同时数据管道刚灌入一条 close=0 的脏行情，有人正好对该标的开局/交易。
- **现象**：注册并发 → 1 成 N 败(400)；零价 → 除零守卫返 0 股/跳过，不 500。
- **危害**：低——两条独立路径各自已兜底，无交叉放大。
- **叠加叶子**：TR1{已修} + A1.2{已修}。

### X5 锁序反转被未来特性激活 【当前不可达·潜在高破坏】
- **触发前提（当前不成立）**：某特性允许同一用户的两个 in-progress 对局并发操作，且 undo 与 settle 对 user_points/account 以相反序加锁而未被 session 锁串行化。
- **现象**：`undo(s1)` 持 user_points(U) 等 account；`settle(s2)` 持 account 等 user_points(U) → MySQL Deadlock，一方被回滚 500。
- **危害**：潜在高——但当前被"同 session 串行 + account 按 session 隔离"拆除。**列为架构雷区，防回归**。

## 五、风险暴露窗口 & 概率×破坏性评估

| 场景 | 暴露窗口 | 概率 | 破坏性 | 综合 |
|---|---|---|---|---|
| X1 多房间集中强结 | 房间集中到期的瞬间（活动结束/整点）；窗口 = 池耗尽到恢复 | **高**（有活动/整点必现） | **高**（局部雪崩） | **P0 优先** |
| TB1/X5 锁序反转 | 需未来特性激活 | 当前**极低** | 高 | 防回归 |
| X2 跨午夜写放大 | 零点前后数分钟 | 中 | 中（性能抖动） | P2 |
| B1.2 真人撞前缀 | 持续（只要有此类注册） | 中 | 中（单用户隐身） | P1 |
| X3 部分成员结算失败 | 数据异常时 | 中 | 低（已兜底） | 监控即可 |
| X4 注册+零价 | 偶发 | 低 | 低 | 监控即可 |

**破坏性最强且概率高的是 X1**——它把"连接池放大(TB2)+房间读路径持锁写(SPOF-2)+成员在玩(TR3)"叠加成局部雪崩，是本轮架构层面**最该优先治理**的点。

## 七、容错架构优化建议（分期）

### 短期补丁（1–2 周，不动架构）
- **SP-1【P0】房间强结移出读路径**：`view()` 不再同步强结——改为**到期由定时任务/异步触发**结算，`view` 只读当前状态。直接拆解 X1 的"读路径持锁写"（SPOF-2 + RW1）。最小版可先给强结加分布式/DB 锁 + 限并发，避免多房间同时强结。
- **SP-2【P0】显式连接池 + 超时降级**：已配池 20；再加 `connection-timeout` 合理值 + 对房间强结的单成员结算设超时，避免单员卡死钉住连接（已部分，补超时）。
- **SP-3【P1】注册前缀保留字**：拒绝 `smoke_/btncheck_/shot_` 开头注册，闭合 B1.2。
- **SP-4【P1】锁序统一**：把 undo 的加锁序改成与 settle 一致（`session → account → user_points`），**主动拆除 TB1 雷**，不留给巧合。
- **SP-5【P2】前缀单源 + 埋点哨兵落地**：E1 空窗 / E4 脱敏漏网 / E6 零价，对准 B1.3/B3.3/A1.2。

### 中期重构（1–2 个月）
- **MP-1 结算与房间解耦**：引入结算领域服务 + 幂等结算记录（结算结果落独立表，view 读结果不触发计算），彻底读写分离。
- **MP-2 乐观锁/版本号替代部分悲观锁**：对 session/account 高频路径评估用 `@Version` 乐观锁 + 重试，降低锁等待与死锁面。
- **MP-3 并发测试基建**：`@Concurrent` 测试基类，把"查-then-写/唯一键/状态迁移/锁序"接口纳入强制并发用例（FI-1~FI-8 自动化）。
- **MP-4 可观测性平台化**：Hikari/慢 SQL/死锁/5xx 进看板 + 告警，替代 grep 关键字。

### 长期架构调整（季度级）
- **LP-1 水平扩展就绪**：限流/会话/缓存外置（Redis），应用无状态化，解 SPOF-1；多实例前这是前提。
- **LP-2 结算异步化/事件驱动**：对局结束 → 事件 → 结算消费者（可重试、可幂等、可削峰），房间强结走同一条异步链，根治 X1。
- **LP-3 读写分离 / 榜单物化**：榜单走只读副本或物化视图 + 短 TTL 缓存，把高频只读与结算写彻底分流。
- **LP-4 时间权威统一**：每日一猜等"每日限次"迁服务端判定，消除客户端时钟竞态（RW2）。

---

**FTA 总结论**：本轮 13 bug 修复已把**崩溃类与数据错乱类的活跃叶子**基本闭合；FTA 推演暴露的**深层风险不再是单个 bug，而是三处架构耦合**——① 房间强结在读路径持锁同步执行（X1，P0）；② undo/settle 锁序反转（TB1，当前被巧合拆除，SP-4 主动消除）；③ 单实例/单库 SPOF（LP-1）。短期 SP-1/SP-4 直接拆 X1 与 TB1 两颗最危险的雷，长期 LP-2 结算异步化是根治方向。
