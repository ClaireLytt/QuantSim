## 1. 幂等性与业务状态机审计报告

### 1.1 核心状态机与非法跳转

**对局生命周期**：`IN_PROGRESS → SETTLED`（终态，单向）。
- 合法：start→IN_PROGRESS；tick/trade 在 IN_PROGRESS 内自转；settle→SETTLED。
- **非法跳转防护**：所有写入口（tick/trade/settle/undo/placeOrder）先 `getSessionWithLock` + `requireInProgress`，
  对 SETTLED 对局一律 400。**无非法跳转**。✅

**房间生命周期**：`OPEN → SETTLED`（终态）。
- 迁移点：全员完成 或 到期强结（`evaluateTransitions`，持 room 锁）。
- **可接受的中间态**：房间 SETTLED 但某成员仍 IN_PROGRESS（强结失败）——**设计内**，重入幂等。

**每日一猜**（客户端）：`未玩 → 进行 → 完成`，标记 `prog.daily.date`。本轮已修"开局即落标记"防跨夜/刷新。
无服务端奖励，非权威。

**赛季榜单**：无显式状态机；`season` 字段开局固化（跨零点不串季）。✅

**任务奖励领取**：`taskFlags` 位图 + `taskDate` 日重置；signin/spin 按 `lastSignIn/lastSpin` 日期。终态=当日已领。

### 1.2 写接口幂等性

| 接口 | 幂等机制 | 结论 |
|---|---|---|
| settle | 行锁 + requireInProgress | ✅ 重复→400 |
| register | 唯一键 + catch→400 | ✅ |
| daily/start | uk_user_daily + catch→400 | ✅ |
| signin/spin | 行锁 + 日期判定 | ✅ 并发双签被行锁串行化 |
| redeem | 行锁 + 原子查扣 | ✅ 无超扣 |
| **awardSettle 发分** | **每对局一次（隐含），但无每日/对局数上限** | ⚠ 见安全 SEC-1：可"无限开局"绕过 |
| room join | room 锁 + max_players | 需补并发用例确认不超员（混沌 C12） |

### 1.3 缺状态锁/版本号的流程

- **全部关键写走悲观行锁**（session/account/room/user_points/daily），**无乐观锁**。高频对局操作串行化
  （正确但限并发吞吐）。
- **缺口**：`AuthService` 认领游客行 check-then-act **无锁定重读**（技术债 D1.4，丢更新窗口）。

### 1.4 加固方案

- **SEC-1 根治**（P0）：发分绑定"有效对局"（≥1 交易/推进）+ 每日发分上限 + winStreak 封顶（见安全审计）。
- **乐观锁试点**：session/account 高频路径评估 `@Version` + 重试，降锁等待（技术债 MP-2）。
- **幂等键规范**：一次性动作用唯一键/状态位（已有范例 uk_user_daily/taskFlag）；新发分/领奖接口强制接入。
- 游客认领改 `INSERT IGNORE`/锁定重读。

## 2. DB & 缓存数据一致性审计报告

### 2.1 缓存策略与不一致场景

- **行情缓存**（Caffeine，`StockData`，10min expireAfterWrite）：只读、管道重灌自动过期——**一致性风险低**；
  窗口=最多 10min 的旧行情（可接受，行情本身非实时）。
- **榜单无缓存**：实时查 DB（技术债 D2.3）——无陈旧但 DB 压力大。若引入榜单缓存（建议）需注意
  **`isSelf` 因人而异**：缓存脱敏后主体、isSelf 应用层二次标记。
- **会话 JDBC 落库**：多实例共享、重启不丢——**无进程内会话不一致**。✅
- **限流进程内**（技术债 D3.1）：多实例各算各的——**唯一的进程内状态不一致缺口**。

### 2.2 读写时序 / 失效 / 脏数据

- **强结写 + 榜单读并发**（仿真 X2）：榜单 RR 快照读不被写阻塞，`season` 开局固化→不串季，**数据一致**。
- **结算半提交**：settle 单事务原子，无半提交；房间强结单成员 REQUIRES_NEW 独立提交，部分成功是**设计内**。
- **行情重灌失败**：管道 upsert 幂等；失败则缓存保留旧值到过期——短暂旧数据，非脏。

### 2.3 定时对账任务（建议新增）

```
对账-1 榜单真实性: 每小时扫 已结算对局数>0 但某公开榜返回0条 → 告警 (过滤误杀全部)
对账-2 积分守恒: user_points.balance 对账发分流水 (若引入流水表); 当前无流水, 建议补 points_ledger
对账-3 房间收敛: status=OPEN 且 expires_at < NOW()-1h 的房间 → 告警 (强结未触发/卡死)
对账-4 孤儿会话: IN_PROGRESS 且 updated_at 超 N 天 → 标记/清理
对账-5 数据质量: daily_price.close<=0 计数 > 0 → 告警 (脏行情, 零价守卫已止血)
```

### 2.4 校验点 / 告警规则

- 榜单空窗（对账-1）、房间不收敛（对账-3）、零价脏数据（对账-5）即时告警；积分异常（对账-2，引入流水后）
  日级对账。

## 3. 灾备与数据恢复方案

### 3.1 故障场景推演

| 故障 | 现状影响 | 恢复 |
|---|---|---|
| **MySQL 实例宕** | 全站不可用（单库 SPOF-1） | 重启/切备库；无主从则靠备份恢复 |
| 主从切换 | **当前无主从**——不可用 | 需先建主从（LP） |
| 缓存崩溃 | Caffeine 进程内, 随应用重建, 仅短暂回源 DB | 自愈 |
| 服务实例重启 | 会话 JDBC 落库不掉线；进程内限流/缓存重置（短暂宽松） | 自愈；**部署按体检④重启后验证** |

### 3.2 数据损坏场景

- **部分表错乱**（如测试数据入库）：过滤已不展示，清理走 SOP-5（备份→DELETE by 前缀）。
- **事务半提交**：业务事务原子，不产生半提交；跨服务仅房间强结 REQUIRES_NEW，部分成功可重入收敛。

### 3.3 RTO / RPO 目标（建议）

| 等级 | RTO | RPO | 手段 |
|---|---|---|---|
| 当前（单库无备） | 小时级（手工恢复） | 取决于最近备份 | **不达标, 需改进** |
| 短期目标 | < 30min | < 15min | 定时 mysqldump + binlog |
| 中期目标 | < 5min | < 1min | 主从 + 自动故障转移 |

### 3.4 定点回滚 / 校验 / 补偿

- **代码回滚**：git 重建（非切镜像），预置 `ROLLBACK_TO`（见 release-acceptance SOP）。
- **数据回滚**：恢复前 `mysqldump` 备份；定点删除/修正走参数化 SQL + 备份。
- **恢复后补偿**：榜单/积分对账（模块2）跑一遍；对"恢复窗口内丢失的发分/结算"用幂等键重放或人工补偿。

## 4. 第三方依赖风险审计

### 4.1 依赖现状

- **Spring Boot 3.3.4**（2024-09 发布）、**Java 17**、mysql-connector-j、Flyway、Lombok、Caffeine——**版本较新，
  无明显老化**。3.3.x 为当时稳定线。
- **无第三方限流/缓存重组件**（限流自研、缓存用 Spring Cache+Caffeine）——**攻击面小**。

### 4.2 底层组件边界坑（已踩/需防）

- **Spring 事务传播**：REQUIRED 嵌套的 rollback-only 污染（本轮 #3 已踩）；REQUIRES_NEW 连接占用（已用）。
- **JPQL**：`NOT LIKE ... ESCAPE` 文本块转义（本轮调试踩过双反斜杠）；无 OpenAPI 导致契约无机器校验。
- **JPA + RR 隔离**：check-then-act 快照读看不到并发提交，**护栏全靠唯一键**（易漏）。
- **Hikari 默认池 10**（已显式配 20）；`createDatabaseIfNotExist` 仅开发便利，生产应预建库。

### 4.3 升级风险

- Spring Boot 3.3→3.4/4.x：注意 `spring.factories` 弃用、actuator 端点变化、Hibernate 6.x 行为。升级前跑全套
  84 测试 + 冒烟。
- Java 17→21：LTS，兼容性好，但虚拟线程等新特性需评估对悲观锁模型的影响。

### 4.4 依赖管理策略

- **接入 Dependabot / OWASP dependency-check** 到 CI（当前**无依赖扫描**）——季度安全更新。
- 锁定版本（已用 parent BOM），升级走小版本 + 全测试门禁。

## 5. 可观测性体系设计（完整重设计）

### 5.1 分层指标

| 层 | 指标 |
|---|---|
| **业务** | 发分速率/用户、榜单查询量、每日挑战参与、房间强结次数/失败率、兑换/盲盒次数、SEC-1 可疑高频 start→settle |
| **系统** | 应用 5xx by path、RT p50/p95/p99、JVM GC/堆、实例存活 |
| **数据库** | 慢查询(digest)、QPS、Com_commit/rollback、死锁、Threads_connected |
| **事务** | Hikari active/idle/pending、REQUIRES_NEW 占用、rollback-only 事件 |

### 5.2 结构化日志规范

- 统一 `evt=<name> userId=.. sessionId=.. k=v`，**用户名只落脱敏值/userId**（见 observability 埋点目录 E1-E7）。
- 错误分类：`biz`(400 业务)、`auth`(401)、`notfound`(404)、`sys`(500) —— 便于按类聚合。

### 5.3 告警分级（消除风暴）

| 级 | 触发 | 响应 |
|---|---|---|
| **P0** | health 非 UP / 5xx>2% / `UnexpectedRollbackException`>0 / 连接池耗尽 | 立即呼叫 + 考虑回滚 |
| **P1** | `/rooms`·`/register`·`/daily` 500>0 / 榜单空窗 / Deadlock | 1h 内处理 |
| **P2** | 慢 SQL p95 超阈 / 零价守卫命中 / 强结失败频次升高 | 工作时间处理 |
| **P3** | 盲盒/发分速率异常（SEC 监控）/ 每日一猜 cross-midnight | 趋势观察 |
- **防风暴**：同类事件 5min 聚合 + 去重；P2/P3 进日报不即时呼叫。

### 5.4 链路追踪

- 关键链路埋 traceId：**结算链**（settle→doSettle→awardSettle→bias）、**榜单链**（query→filter→mask→isSelf）、
  **房间强结链**（view→evaluateTransitions→settleIsolated×N）。当前无 APM，先用 MDC traceId 贯穿日志。

### 5.5 Dashboard 设计

- **核心大盘**：5xx/RT/QPS、Hikari 连接、健康、发分速率、榜单查询量。
- **故障专项盘**：rollback/deadlock/连接池 pending、房间强结成败、零价命中、SEC 可疑刷分（高频 start→settle）。

## 7. 账号隔离与权限安全审计

### 7.1 账号类型与越权推演

| 类型 | 边界 | 越权风险 |
|---|---|---|
| 注册用户 | 对局/房间仅本人（`requireAccess`→404 不泄露存在性） | ✅ 已收口 |
| 邮箱用户 | 同上 + 榜单脱敏 | ✅ |
| 游客匿名 | 对局开放（设计）、受保护接口 401 | 低（游客记录非高价值） |
| 测试账号 | 榜单过滤排除 | ⚠ 真人撞前缀被隐身（SEC/已知限制） |

- **跨账号泄露**：`requireAccess` 对按 ID 操作的 `/{sessionId}/**` 校验属主（本轮前已修的高危#1）；
  `BlindDates` 防竞技剧透。**无横向越权**。

### 7.2 查询是否强制携带账号过滤

- 本人视角接口（/me/**、对局）均带 `userId`/属主校验；公开榜**有意**不带（榜本就公开），但**脱敏 + 测试账号
  过滤 + isSelf** 已处理隐私与身份。✅

### 7.3 脱敏一致性

- `PublicNames.mask` 覆盖 5 个公开榜；好友房间**有意豁免**（互相认识）。`isSelf` 覆盖需自我识别的 2 榜。
  **一致**（本轮联动校验已验证无缺口）。

### 7.4 权限校验统一规范

- 按 ID 操作一律 `requireAccess(id, CurrentUser.idOrNull)`；记战绩走 `resolve` 不直接 `findOrCreate`；
  公开展示过 `PublicNames`（脱敏+过滤）；受保护前缀进 `AuthFilter`。**已成规范，继续坚持**。

## 8. 资源成本优化方案

### 8.1 索引优化（有真实缺口）

| 查询 | 现状 | 建议 |
|---|---|---|
| 收益榜 ORDER BY return | ✅ 走 `idx_sessions_return(status,return DESC)` | 保持 |
| **夏普榜 ORDER BY final_sharpe** | ⚠ **无 sharpe 索引 → filesort** | 加 `idx(status, final_sharpe DESC)` |
| **积分榜 ORDER BY balance** | ⚠ **无 balance 索引 → filesort** | 加 `idx_points_balance(balance DESC)` |
| 赛季过滤 season | 后过滤（无 season 索引） | 数据量大后加 `idx(status, season, return DESC)` |
| 竞技场榜 total_return | ✅ `idx_bt_return` | 保持 |
| **SEC-3 榜单去重** | 无 GROUP BY | 加 per-user 去重（兼顾正确性与性能） |

### 8.2 缓存资源

- Caffeine `maximumSize=64` 行情条目，占用极小；榜单引入短 TTL 缓存（10-30s）可**砍数量级 DB 查询**
  （榜单是最高频只读）。

### 8.3 定时任务 / 后台作业

- 数据刷新 `refresh.py`（夜间低峰，默认关）、对账任务（建议，低频）——资源消耗低。
- **房间强结移出读路径后**改为定时/异步，需评估其调度资源（批量小，低）。

### 8.4 资源优化

- 榜单缓存（降 DB QPS）+ 补 2 个排序索引（消 filesort）是**最高性价比**；连接池 20 对常规负载充裕
  （仿真峰值 7），无需扩。整体单实例成本低，优化重点在**查询效率**而非扩容。

## 11. 精简版总结（给产品/管理层）

**结论一句话**：本轮 13 bug 已全部修复并通过多维验证（84 测试/多层体检/94 万次仿真全绿）；**综合分析新发现
2 个高危经济漏洞（可被单账号脚本无限刷积分），是当前最该优先堵的问题**。

**现在最该做的 3 件事（1 个月内）**：
1. **堵刷分漏洞**（SEC-1 结算发分加约束 / SEC-2 盲盒改负 EV）——否则积分榜与奖励体系会被轻易刷爆。
2. **拆一颗低成本的死锁雷**（undo/settle 锁序统一）——极小改动，防未来功能触发。
3. **补灾备**（定时备份达到"最多丢 15 分钟数据"）——当前单库无备份是最大的"黑天鹅"敞口。

**健康面（做得好的）**：并发安全（行锁串行化，无双花/超扣）、跨零点防刷（服务端时钟）、越权防护
（属主校验+脱敏）、工程纪律（无 XSS、字段名访问、会话落库）、自动化体检矩阵已成形。

**中长期方向**：把"对局结算"从读路径同步执行改为**异步事件驱动**，并让应用**无状态化支持水平扩展**——
这两步能同时解决性能尾部风险（雪崩）与单点可用性（SPOF）。

**风险敞口排序**：经济刷分(P0,现在) > 死锁雷(P0,极小成本) > 灾备缺口(P1) > 性能尾部与榜单灌水(P1) >
架构单点(长期)。按此路线推进，QuantSim 可从"功能完整、单点可用"演进到"抗刷、抗故障、可扩展"。
