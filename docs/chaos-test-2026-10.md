# QuantSim 混沌测试矩阵 · 2026-10（基于本轮 13 bug）

> 用"真实用户异常操作链路"去压本轮修复点的边界。每条含：操作步骤、预期结果、风险等级、
> **对应修复/是否已覆盖**。风险等级 = 若预期不成立的线上危害（高/中/低）。
> 带 ✅ 的已由本轮修复或测试兜住；带 ⚠️ 的是残留边界，需人工验证或留观测。

---

## 一、弱网 / 页面反复刷新

### C1 结算请求发出后弱网超时，用户刷新页面
- **步骤**：对局进行中点"结算" → 请求发出但弱网下响应未回 → 用户刷新页面 → 重新进入对局。
- **预期**：服务端已用行锁 + `requireInProgress` 保证幂等——若首次请求实际已提交，刷新后看到"已结算"状态；若未提交，可重新结算。**不会出现双重结算或 500**。
- **实测佐证**：重复 `POST /settle` 返回 **400「对局已结算」**（非 500），天然幂等。
- **风险**：**低** ✅（行锁 + requireInProgress 兜住）

### C2 停在"事件回放"/各视图刷新直达
- **步骤**：切到事件回放页 → F5 刷新（URL 直达该视图）。
- **预期**：场景库数量正常显示（不再空白）。其余视图（每日/研究所/擂台）同样有启动兜底。
- **风险**：**低** ✅（本轮 #13 event 启动兜底；其余视图原有兜底）

### C3 弱网下榜单/每日接口超时
- **步骤**：限速到 2G → 反复进榜单页/每日页。
- **预期**：失败分支按**状态码**判断（非中文文案）——游客的 401 静默、其余才 toast；页面不因一次请求失败整页崩。网关返回 HTML/英文错误也不误弹。
- **风险**：**低** ✅（本轮 #14 status 判断；各页 catch 留空兜底）

### C4 登录态在弱网/会话过期后操作受保护接口
- **步骤**：登录 → 放置到会话过期 → 点"每日挑战/房间/我的"。
- **预期**：401 由入口引导登录，不弹无意义错误；重登后恢复。
- **风险**：**低**（AuthFilter + 前端 401 处理）

## 二、跨午夜 / 跨日期（每日一猜重点）

### C5 每日一猜跨零点完成
- **步骤**：23:59 开局"每日一猜" → 00:01 完成。
- **预期**：成绩记在**开局当天**名下（不写成第二天），不吞第二天名额。
- **风险**：**中** ✅（本轮 #6/#9：开局即落当天标记，结束只更新得分、不重写日期）

### C6 每日一猜开局后刷新想重开
- **步骤**：开局 → 不完成 → 刷新页面 → 再点"每日一猜"。
- **预期**：提示"今天已玩"，**不能无限重开**。
- **风险**：**中** ✅（本轮 #9：开局即落标记）

### C7 服务端全服"每日挑战"跨零点
- **步骤**：临近零点开"每日挑战"对局 → 跨零点后推进/结算。
- **预期**：挑战归属 `challengeDate`（开局日），跨零点不影响该局；次日是新题。
- **风险**：**中**（`challengeDate` 固定在开局，需验证跨零点推进不串题）

### C8 本地时钟与服务端时区不一致
- **步骤**：客户端改系统时区/时钟到次日 → 操作每日一猜（本地）与每日挑战（服务端）。
- **预期**：每日一猜用本地 `todayStr()`（客户端时钟）；每日挑战用服务端 `GAME_ZONE`（上海）——两者口径不同是设计，**不应因客户端改钟拿到双倍服务端名额**。
- **风险**：**中** ⚠️（每日一猜是纯本地防刷，客户端改钟理论可绕过本地限制；但它无服务端奖励，危害有限。服务端每日挑战不受客户端时钟影响——需确认）

## 三、快速连续点击 / 多账号并发

### C9 快速连点"结算"
- **步骤**：对局结束页疯狂连点"结算"按钮。
- **预期**：首次 200 结算，后续请求被行锁串行化后看到已结算 → 400「对局已结算」；无双重结算、无 500。
- **风险**：**低** ✅（行锁 + requireInProgress，实测 400）

### C10 快速连点"开始每日挑战"/两标签页同时开
- **步骤**：同账号两个标签页同时点"开始每日挑战"。
- **预期**：一个成功进局，另一个 **400「今天已经玩过」**；无 500、无双开。
- **风险**：**中** ✅（本轮修复 + 回归用例 T-06：并发双开稳定 1×200+N×400，死锁已消除）

### C11 并发同名注册
- **步骤**：多端几乎同时注册同一用户名。
- **预期**：一个成功，其余 **400「用户名已被注册」**；无 500。
- **风险**：**中** ✅（本轮 #5：saveAndFlush + catch 转 400）

### C12 多账号同时抢同一房间最后一个位
- **步骤**：房间剩 1 个位 → 多账号同时 join。
- **预期**：一人成功，其余"房间已满"业务提示；人数不超 `max_players`(8)。
- **风险**：**中** ⚠️（本轮未专门改房间 join 并发；`max_players` 约束 + 悲观锁需验证不超员——建议补并发用例）

### C13 多个房间同时到期被并发访问（连接池压力）
- **步骤**：造多个各 8 人、同时到期的房间 → 并发打它们的 `GET /{code}`。
- **预期**：各房间正常强结 → SETTLED，无 500；连接池不耗尽（`connection timeout`）。
- **风险**：**中** ⚠️（功能正确性 ✅ 已修 #3；但 REQUIRES_NEW 单请求占 2 连接、默认池 10，~5 并发即饱和——见性能审计，上线前压测）

## 四、特殊数据 / 空态 / 零价

### C14 邮箱账号上榜与自我识别
- **步骤**：邮箱账号打榜 → 查看每日百分位、颁奖台。
- **预期**：榜上名字脱敏（`cl***@…`），但"我的百分位"、颁奖台称号正常（靠 isSelf，非名字比对）。
- **风险**：**高** ✅（本轮 #2：isSelf 标记；回归用例已覆盖）

### C15 极短邮箱账号脱敏
- **步骤**：注册 `ab@x.com` 类极短邮箱 → 上榜。
- **预期**：完全遮挡为 `***@x.com`，local 不泄露。
- **风险**：**中** ✅（本轮 #4：短 local 全遮；PublicNamesTest 覆盖）

### C16 真人注册名撞测试前缀
- **步骤**：真实用户注册 `smoke_gun` 之类 → 打榜。
- **预期**：**当前会从公开榜静默消失**（被当测试账号过滤）——这是**已知限制**，待注册保留字修复。
- **风险**：**中** ⚠️（已知限制，见 Release Notes；监控"榜单空窗"兜底）

### C17 空数据历史记录
- **步骤**：新服/新赛季无任何结算记录 → 进各榜/个人主页/每日榜。
- **预期**：榜单显示"暂无记录"空态；每日百分位隐藏；个人主页统计显示 `--`；无 `NaN`/`undefined`/报错。
- **风险**：**低** ✅（各榜有空态；数值字段 null 兜底）

### C18 擂台含 null 字段的旧记录
- **步骤**：查看含历史 null 回撤记录的擂台榜/终榜。
- **预期**：回撤显示 `--`，不显示 `+0.0%`/`NaN%`。
- **风险**：**低** ✅（本轮 #10：ddText 兜底）

### C19 行情价格为 0（脏数据）
- **步骤**：（构造）插入 close=0 的行情 → 触发对局 tick / 开局 / AI 调仓 / 自动策略下单。
- **预期**：后端除法防护返 0 股/跳过，不 500；前端自动策略下单数量防零价（不产生 NaN）。
- **风险**：**中** ✅（本轮 #7 后端 + 联动校验补的前端 app.js 守卫；建议补集成用例）

## 五、结算中途关闭 / 请求中断

### C20 结算请求发出后立即关闭页面
- **步骤**：点"结算" → 服务端处理中 → 用户关标签页/杀进程。
- **预期**：服务端事务要么完整提交（对局 SETTLED）要么回滚（保持 IN_PROGRESS），**无半结算状态**（结算是单事务）。下次进入看到一致状态。
- **风险**：**低** ✅（settle 是单 `@Transactional`，原子提交；客户端中断不影响服务端事务完整性）

### C21 推进(tick)请求中断后重试
- **步骤**：点"推进下一天" → 请求中断 → 重试。
- **预期**：tick 是单事务 + 行锁；中断未提交则状态不变可重试，已提交则重试会推进到再下一天（用户需看清当前交易日）。无脏状态。
- **风险**：**低**（单事务原子；UI 应以服务端返回的 currentTradeDate 为准）

### C22 房间强结过程中被打断（某成员结算 I/O 失败）
- **步骤**：房间到期 view 触发强结 → 某成员结算时 DB 瞬断/行情缺失。
- **预期**：该成员的独立事务回滚（不污染房间），房间仍迁 SETTLED，页面 200；失败进 warn 日志。
- **风险**：**中** ✅（本轮 #3：settleIsolated REQUIRES_NEW；回归用例覆盖"部分成员失败仍收敛"）

### C23 交易请求中断后账户状态
- **步骤**：买入/卖出请求发出 → 中断 → 刷新看账户。
- **预期**：交易是单事务（含账户扣款 + 流水），原子提交；中断未提交则账户不变，无"扣了钱没持仓"类半成品。
- **风险**：**低**（单事务原子 + 行锁）

## 汇总：残留需人工验证的边界（⚠️）

| 场景 | 为什么需人工验 | 建议 |
|---|---|---|
| C8 客户端改钟绕每日一猜 | 纯本地防刷，无服务端兜底 | 确认无服务端奖励可被刷；如需严格，每日一猜也服务端化 |
| C12 房间满员并发 join | 本轮未专门改，靠悲观锁 | 补并发 join 用例，断言不超 max_players |
| C13 多房间并发强结 | 连接池峰值 | 按性能审计场景 2 压测 |
| C16 真人撞测试前缀 | 已知限制 | 注册保留字（待修）+ 榜单空窗监控 |
| C19 零价行情 | 已加前后端防护但无集成用例 | 补 close=0 的集成测试 |

**结论**：13 个修复点在混沌操作下大多**已被行锁/单事务/幂等/空值兜底**稳稳接住（C1/C5/C6/C9/C10/C11/
C14/C18/C20 等）；真正要盯的残留边界集中在**房间并发（C12/C13）**、**客户端时钟（C8）**、**已知前缀限制
（C16）**、**零价集成用例缺口（C19）**——均已在性能审计/Release Notes/复盘里登记对应动作。
