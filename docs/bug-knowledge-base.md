## 一、问题归类统计

| 根因分类 | 数量 | 本轮案例编号 |
|---|---|---|
| 分页查询（过滤与 LIMIT 顺序） | 1 | #1 |
| 前后端状态判断（脱敏后身份比对） | 1 | #2 |
| 事务传播（父事务被 rollback-only 污染） | 1 | #3 |
| 并发竞态（唯一键 / 死锁 / 限流 map） | 3 | #5、#13、#9(死锁) |
| 空值 / 边界值（除零、null 展示、短输入） | 3 | #4、#7、#11 |
| 异常处理（吞异常、文案判断、时机错位） | 4 | #6、#8、#10、#12 |

**最值得记住的三条教训：**
1. **过滤必须发生在 LIMIT 之前**——数据层的事，别留到应用层分页后补。
2. **脱敏改变了可见数据，所有"按可见值做判断"的逻辑都要重审**——身份比对尤甚。
3. **`@Transactional` 嵌套里，内层抛异常会把整个物理事务标记 rollback-only，catch 了也救不回**——要隔离就用 `REQUIRES_NEW`。

## 二、Bug 台账表格

### 【高危】

#### #1 榜单挤位
- **现象**：真实玩家结算后进不了 TOP N，排在测试账号后面的被"挤掉"。
- **根因分类**：分页查询。过滤发生在 `LIMIT N` **之后**——先取满 N 条再剔除测试账号，剔掉几条就少几条。
- **触发条件**：`smoke_/btncheck_/shot_` 自动化账号的成绩进入了分页窗口。
- **修复**：过滤条件下沉进 JPQL `WHERE`（5 个公开榜查询统一加 `username not like 'smoke\_%' escape '\'` 等），分页前排除。
- **预防手段**：
  - 规范：任何"取 TOP N + 过滤"的查询，过滤必须在 SQL/JPQL 层、分页之前。
  - 测试：造"测试账号高分在前 + 真实玩家"的数据，断言榜单真实玩家**数量不减**。
  - 审查项：见到 `.stream().filter().limit()` 或 service 层对分页结果再 filter，一律打回数据层。

#### #2 脱敏回归
- **现象**：邮箱注册用户进榜后，"我的百分位"、颁奖台徽章静默消失。
- **根因分类**：前后端状态判断。前端用 `entry.username === Auth.user.username` 认"自己"，但后端已把榜单用户名脱敏（`claire@x → cl***@x`），永远不相等。
- **触发条件**：用邮箱注册 + 上榜 + 前端有"高亮/标记自己"的逻辑。
- **修复**：DTO 增 `isSelf` 后端标记（后端用 `userId` 比对，不受脱敏影响），前端改读标记。
- **预防手段**：
  - 规范：**展示值脱敏后，不得再用展示值做业务判断**；身份判断一律用服务端下发的稳定标记（id/flag），不用显示名。
  - 测试：邮箱用户上榜 → 断言自己那行 `isSelf=true` 且 username 已脱敏；他人视角 `isSelf=false`。
  - 审查项：新增脱敏字段时，全局搜该字段的 `===`/`equals` 比对点，逐一确认是否受影响。

#### #3 房间永久 500
- **现象**：房间到期后房间页每次访问都 500，永远结算不了。
- **根因分类**：事务传播。到期强结循环里某成员 `settle()` 抛异常，该 `settle` 与外层 `view()` 是同一物理事务（`REQUIRED`），异常把事务标记 **rollback-only**；`catch` 住了也没用，提交时 `UnexpectedRollbackException` → 整个请求 500，下次重入重蹈覆辙。
- **触发条件**：房间成员对局结算失败（行情缺失 / 并发已结算）且该成员属于到期强结批次。
- **修复**：抽 `settleIsolated`（`@Transactional(REQUIRES_NEW)`），单成员失败只回滚自己的独立事务，不污染父事务；父循环 catch 后继续，房间照常迁 `SETTLED`，重入幂等。
- **预防手段**：
  - 规范：**循环内调用可能失败的事务方法、且希望"失败一个不影响整体"时，被调方必须 `REQUIRES_NEW`**；否则 catch 是假的。
  - 规范：`REQUIRES_NEW` 内若有 `SELECT ... FOR UPDATE`，确认父事务没持同行锁（同 JVM 两连接互等 = 自死锁）。
  - 测试：构造"部分成员结算失败"场景，断言请求 **200 且房间迁 SETTLED**、连续重入幂等、日志无 `UnexpectedRollbackException`。
  - 审查项：见到 `try { someService.txMethod() } catch` 在事务方法内部，先问"内层标记 rollback-only 了吗"。

### 【中危】

#### #4 短 local 邮箱脱敏不全
- **现象**：`ab@x.com` 脱敏后还是 `ab***@x.com`，local 全暴露，`***` 只是装饰。
- **根因分类**：边界值。"保留前 2 字符"对本就 ≤2 字符的 local 等于没脱。
- **触发条件**：local part 长度 ≤ 2 的邮箱用户名。
- **修复**：local < 3 字符时全遮（`***@x.com`）。
- **预防手段**：脱敏/截断类函数必做"输入短于保留长度"的边界用例；`PublicNamesTest` 已覆盖 `a@ / ab@ / abc@ / @x / @ / null`。

#### #5 并发注册 500
- **现象**：同名并发注册返回 500「服务器内部错误」而非友好提示。
- **根因分类**：并发竞态（TOCTOU）。`findByUsername` 查空 → `save` 撞唯一键 → `DataIntegrityViolation` 未处理 → 500。
- **触发条件**：两请求几乎同时注册同一用户名（或与游客行创建竞争）。
- **修复**：`saveAndFlush` + catch `DataIntegrityViolationException` 转 400 业务提示（catch 后直接抛业务异常收场，不在本事务继续写）。
- **预防手段**：
  - 规范：**"查-then-插"模式对唯一键不安全**；要么 `INSERT IGNORE` + 锁定重读，要么 catch DIV 转业务异常（且 catch 后不得在同事务继续写）。
  - 测试：多线程 + CyclicBarrier 并发打同一入口，断言"一成多败（400），无 500"。

#### #6 并发每日挑战双开 500 → 400
- **现象**：同日第二次开局本该 400「今天已玩」，并发下得到 500。
- **根因分类**：异常处理 + 并发。`uk_user_daily` 唯一键冲突未在 catch 覆盖点暴露。
- **修复**：开局会话 `saveAndFlush` 让冲突落进 `start()` 的 catch 块（转 400）。
- **预防手段**：同 #5；并发用例纳入回归套件。
- **⚠ 关联延伸（回归阶段发现）**：此路径还藏一个**并发死锁 500**——`getOrCreate` 的 `INSERT IGNORE + SELECT ... FOR UPDATE` 在并发首访同日时插入意向锁与行锁交错成 MySQL Deadlock。**内容由日期种子完全确定 → 锁读回写本就多余**，改为 insertIgnore 后直接返回计算值。教训：**确定性数据不要用 FOR UPDATE 回读**。

#### #7 行情除零
- **现象**：价格为 0 的坏行情 bar 导致 tick/开局/AI 调仓 500（`ArithmeticException` / `divide` 无 scale）。
- **根因分类**：空值 / 边界值（脏数据）。
- **触发条件**：`daily_price.close <= 0` 的异常行情。
- **修复**：`TradeMath.maxWholeShares` / `GameAiService` 价格 `signum() <= 0` 时返 0 / 跳过。
- **预防手段**：
  - 规范：`BigDecimal.divide` 必带 scale + RoundingMode；除数来自数据的，先判 `signum() > 0`。
  - 建议：数据入库层（管道 `load_to_db`）拒绝 `close <= 0`，止于源头（交易层兜底只是止血）。

#### #8 限流器清理竞态
- **现象**：key 数超阈值触发清理时，限流可能被短暂旁路（计数记进孤儿队列）。
- **根因分类**：并发竞态。`removeIf` 清理与 `computeIfAbsent` 新建交错，队列被摘后命中计进它。
- **修复**：写完 `putIfAbsent` 把队列挂回；已被重建则放弃本次计数（丢一跳好过整体旁路）。
- **预防手段**：
  - 规范：`ConcurrentHashMap` 上"遍历清理 + 并发写同一 key"必须考虑 compute 与 remove 的交错；优先用两参 `remove(key,value)` 或按时间戳淘汰。
  - 提醒：进程内限流多实例部署前须换集中式（Redis），此竞态只是单机兜底。

#### #9 每日一猜落库时机
- **现象**：23:59 开局、00:01 结束把"已玩"记到第二天吞名额；或开局后刷新即可无限重开当日局。
- **根因分类**：异常处理 / 状态时机。"已玩"标记在**结束时**才写。
- **触发条件**：跨零点完成一局，或开局后刷新页面。
- **修复**：开局成功即落当日标记（结束只更新得分，且记在**开局那天**名下）。
- **预防手段**：规范——"每日限次"类标记应在**动作开始**时落（占位），而非完成时；跨零点与中途刷新都要想到。

### 【低危】

#### #10 擂台 null 展示
- **现象**：旧回测记录 `maxDrawdown` 为 null，榜上显示 `+0.0%`（还配红色 neg 样式）或 `NaN%`。
- **根因分类**：空值。`Number(null)=0`、`Number(undefined)=NaN` 渗进展示。
- **修复**：null/undefined 显示 `--`。
- **预防手段**：前端渲染后端数值字段，一律 `v == null ? "--" : fmt(v)`；`Number()` 前先判空。

#### #11 游客昵称碎片化
- **现象**：隐私模式下游客每次操作生成新随机昵称，同一局的预回测与提交顶着两个身份。
- **根因分类**：边界值（存储不可用）。`localStorage.setItem` 抛异常后名字没持久化。
- **修复**：setItem 失败时把名字缓存在模块级变量复用。
- **预防手段**：规范——依赖 `localStorage` 的"稳定标识"必须有内存兜底；storage 读写一律 try/catch 且设计成读空也能正确工作。

#### #12 mine 通关统计
- **现象**："小游戏通关数"虚高——开一局重生 / 破一个案就被计入通关。
- **根因分类**：异常处理 / 语义判断。按"存档键存在"统计，但 reborn/qdetect 在**进行中**就写键。
- **修复**：这两个键改为检查通关字段（`best`）存在，而非键存在。
- **预防手段**：规范——"完成数"统计要看**完成语义字段**，不要用"有存档"近似；新增小游戏在 `mine.js` 的 `GAME_BEST_KEYS` 登记并确认其存档语义。

#### #13 event 视图刷新空白
- **现象**：停在"事件回放"视图刷新页面，场景库数量不显示（直到切走再切回）。
- **根因分类**：状态时机。只在 `qs:view` 事件时 `load()`，无启动兜底。
- **修复**：文件尾补 `if (!$("view-event").hidden) load()`。
- **预防手段**：规范——每个视图 IIFE 若依赖 `qs:view` 触发加载，必须有"刷新直达本视图"的启动兜底（参照 daily/relics 惯例）。

#### #14 api 错误判断依赖中文文案
- **现象**：`api()` 失败分支用 `e.message.includes("登录")` 判断是否静默，后端文案改成英文/网关返回 HTML 时，游客每次进页都弹无意义 toast。
- **根因分类**：异常处理。用文案子串做分支判断。
- **修复**：`api()` 错误对象附 HTTP `status`，调用方按 `e.status !== 401` 判断。
- **预防手段**：规范——**永远不要用错误文案子串做分支**；按状态码 / 错误类型判断。注意网络层失败（`TypeError`）无 `status`，分支要对 `undefined` 安全。

## 三、新增编码检查规则（PR 评审时强制检查）

> 以下为本轮沉淀的硬性检查项，PR 评审逐条过。

**事务**
- [ ] 事务方法内 `try/catch` 调用另一事务方法，是否清楚内层异常已把物理事务标记 rollback-only？要隔离失败必须 `REQUIRES_NEW`。
- [ ] `REQUIRES_NEW` 方法内的 `SELECT ... FOR UPDATE` 是否与父事务持有的行锁冲突（自死锁）？
- [ ] catch `DataIntegrityViolationException` 后是否在**同一事务**继续读写？（flush 已失败，会在提交时 500——改用 `INSERT IGNORE` 或 catch 后直接抛业务异常收场）

**分页 / 查询**
- [ ] "取 TOP N + 过滤"的过滤是否在 SQL/JPQL 层、分页之前？禁止对分页结果再 `.filter()`。
- [ ] 同一过滤口径是否散落多处（Java 常量 + 多段 JPQL）？双源必有漂移，考虑单一来源。

**并发**
- [ ] "查-then-插"对唯一键是否做了并发保护（INSERT IGNORE / catch DIV）？
- [ ] 确定性内容是否误用了 `SELECT ... FOR UPDATE` 回读（本可直接计算返回，避免死锁）？
- [ ] `ConcurrentHashMap` 的遍历清理与并发写同 key 的交错是否安全？

**空值 / 边界**
- [ ] `BigDecimal.divide` 是否带 scale + RoundingMode？除数来自数据的是否判 `signum() > 0`？
- [ ] 前端渲染后端数值字段是否 `v == null ? "--" : fmt(v)`？`Number()` 前判空？
- [ ] 脱敏/截断函数是否覆盖"输入短于保留长度"的边界？

**状态判断 / 异常**
- [ ] 脱敏后的展示值是否被用于业务判断（尤其身份比对）？身份一律用稳定标记。
- [ ] 分支判断是否依赖错误文案子串？改用状态码 / 异常类型。
- [ ] "每日限次 / 每局一次"类标记是否在动作**开始**时落（防跨零点、防刷新）？
- [ ] 依赖 `localStorage` 的稳定标识是否有内存兜底 + try/catch？
- [ ] 视图 IIFE 依赖 `qs:view` 加载的，是否有"刷新直达"启动兜底？
